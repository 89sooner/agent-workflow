# 신규 사용자 3명 파일럿 진행표

상태: **미실시·선택 사항**. 사용자가 참여자·일정 미정이라고 답했고,
2026-11-06 후속 요청에서 이번 병합·운영 반영의 필수 완료 조건에서 제외했다.
아래 절차와 합격 기준은 나중에 실제 사용자 검증을 진행할 때 사용한다.
미실시를 합격이나 운영 검증 완료로 기록하지 않는다.
P01~P03은 빈 참여 슬롯이며 실제 참여자를 뜻하지 않는다.
개발자 자체 검증과 AI 에이전트 실행을 신규 사용자 실험으로 기록하지 않는다.

## 합격 기준

[승인된 구현 계획](../docs/OBSERVATORY_IMPLEMENTATION_PLAN.ko.md)의 기준을 유지한다.
신규 사용자 3명 모두 진행자의 도움 없이 프로젝트 연결·첫 세션 관측을 10분 안에
완료하고, 제공된 확인 요청을 30초 안에 찾아야 한다. 목표 미달 시 막힌 단계를
수정하고 실제 사용자로 재검증한다. 모르는 수치를 0초·성공으로 채우지 않는다.

## 진행 전 준비

1. 처음 사용하는 참여자 3명과 일정을 확정한다. 이름 대신 식별명을 사용해도 된다.
2. 진행자가 테스트 소스 SHA, 브라우저·OS·도구 버전, 화면 크기를 기록한다.
3. 각 참여자에게 운영과 분리한 프로젝트·관측 home을 제공한다.
4. localhost URL은 같은 컴퓨터에서만 접근할 수 있다. 같은 검증 PC에서 한 명씩
   진행하거나, 참여자 PC에 같은 버전을 설치한다. 사내 원격 서비스가 이미 제공된다고 가정하지 않는다.
5. 관제실은 `watch`로 실행한다. 운영 서버 재시작, 작업 큐 등록, worker 시작은 필요 없다.
6. 실제 도구의 플러그인 활성화·훅 신뢰는 참여자가 내용을 확인한 뒤 수행한다.
   운영 설정이나 계정을 대신 변경하지 않는다. [플러그인 안내](../docs/NATIVE_PLUGINS.ko.md)를 제공한다.
7. 모델 실행이 필요한 경우 참여자에게 테스트 범위와 실행 사실을 알린다.
   기존 운영 대화나 사내 비밀 자료를 테스트 입력으로 사용하지 않는다.
8. 제공할 확인 요청은 원래 도구에서 실제 발생시킨다. 예를 들어 Claude Code의
   질문 도구가 참여자의 답을 기다리도록 한다. 관측 DB를 직접 고쳐 대기 상태를 만들지 않는다.

## 참여자에게 전달할 과제

### 과제 A — 처음 연결

“이 테스트 프로젝트의 일상 세션을 관제실에서 확인하세요. WP 작업을 등록하지
않고 진행하세요. 제공된 사용 안내를 자유롭게 읽어도 됩니다.”

안내를 받는 순간부터 첫 실제 세션·프로젝트·도구가 확인될 때까지 측정한다.
진행자는 답이나 클릭 위치를 알려주지 않는다. 도움이 필요한 경우 개입 내용과
시각을 기록하고 ‘도움 없이 성공’으로 판정하지 않는다.

### 과제 B — 확인 요청 찾기

“원래 에이전트에 답을 기다리는 요청이 있습니다. 관제실에서 해당 요청과
에이전트·프로젝트를 찾아주세요. 실제 응답은 원래 도구에서 처리하세요.”

실제 요청이 화면에 반영되고 과제가 제시된 순간부터 올바른 요청을 선택할 때까지
측정한다. 관측 수신 지연은 별도로 기록한다. 요청 종류와 소유 세션을 확인한다.

### 과제 C — 상태와 근거 이해

“이 에이전트가 현재 작업 중인지, 유휴인지, 과거 기록인지 판단해 주세요.
이력과 마지막 수신 시각으로 판단 이유를 설명해 주세요.”

시간이 지난 기록을 현재 실행으로 오인하는지 기록한다. 화면의 3D 동작만 보고
완료를 단정하지 않는지 확인한다. 이 과제는 A·B의 합격 시간을 대체하지 않는다.

## 기록과 판정

[빈 기록 CSV](READINESS_PILOT_RESULTS.csv)를 실제 수행 후 채운다.
시작·수신·선택 시각, 연결 시간, 요청 탐색 시간, 도움 요청과 실패 단계를 기록한다.
소감은 참여자의 말과 진행자의 해석을 구분한다. 대화 본문·계정·토큰은 기록하지 않는다.

3명 모두 A≤600초·B≤30초·진행자 도움 0회일 때만 계획의 사용성 목표 충족으로
판정한다. 참여자·시간·실제 세션 근거가 없으면 **미완료**다.
현재 실제 운영 URL이나 예약된 진행 일정은 이 문서에서 새로 지정하지 않는다.
