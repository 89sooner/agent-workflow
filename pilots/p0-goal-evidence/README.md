# 조건별 검사 근거의 전후 평가

원래 커밋 `9b0c443da3e72fc490ed487289b5ef62ae0242cf`과 조건별 검사 근거를 적용한 작업 사본을 비교했다. 두 실행 모두 새 Git 저장소·worktree·SQLite 원장에서 실제 CLI를 호출했다. 모델 응답과 파일 쓰기는 고정된 두 CLI 대역이 담당하고, 등록된 생성기 비교와 pytest는 실제 프로세스로 실행했다. 외부 채점기가 최종 파일, 대기·재개 시점, 원장 상태와 JUnit을 읽는다. [기준선](baseline.json) · [변경 후](after.json) · [평가 코드](evaluate.py)

| 사례 | 기준선 | 변경 후 |
|---|---|---|
| 일부 검사 생략 | 필수 번들 검사 1개가 skipped이고 pytest 종료 코드가 0이어서 리뷰 후 완료. 번들이 있는 정상 대조군도 완료 | 필수 번들이 없으면 대기. fixture 일치와 번들 생략이 각 조건에 기록됨. 정상 대조군은 완료 |
| 파일 작성 직후 모델 중단 | 종료 코드 41로 중단. 변경 보존. 같은 작업을 다시 실행해 완료 | 같은 결과. 두 실행 모두 fixture 쓰기 1회, 호출 예산 1회에서 재개 후 누적 3회 |
| 외부 자료와 독립 작업 | 오프라인 조건 수행 후 대기, 입력 없이 재호출해도 모델 호출 누적 2회. 자료를 공급한 뒤 완료 | 같은 결과. 오프라인 조건의 검사 결과가 연결됨. 이 사례에서 생략된 번들 검사는 필수 조건에 들어 있지 않음 |
| 나중 변경이 이전 조건을 깨뜨림 | B가 A를 되돌리자 최종 검사에서 실패해 대기. 다른 형식으로 같은 의미를 구현한 정상 대조군은 완료 | 같은 결과. 실패한 A의 생성기 실행과 통과한 번들 검사를 구별할 수 있음 |

4개 사례에 정상 대조군 2개를 포함해 총 6회씩 실행했다. 모든 변형이 맞아야 해당 사례를 통과로 집계한다. 잘못된 완료는 **1→0**, 잘못된 차단은 **0→0**, 기대한 최종 대기 2건 중 올바른 판정은 **1→2**였다. 세 번째 사례의 입력 전 대기는 중간 관측으로 별도 기록했다. 두 번째 사례에서는 평가 드라이버가 중단된 작업을 한 번씩 명시적으로 재개했다. 실제 사용자의 개입 시간은 측정하지 않았다.

변경 후 각 변형의 최종 기록에서 조건별 근거 참조 **10건**을 확인했다. 채점기는 같은 작업의 실제 검사 ID와 명령, 코드·참조 지문을 대조한다. JUnit 조건은 원본 파일의 SHA-256도 비교하고, 완료된 작업에서는 독립 리뷰 기록이 동일한 검사 ID를 인용하는지 확인한다. 기준선에는 조건별 참조가 없다. 보고서에는 임시 원장이 정리된 뒤에도 검사와 조건을 서로 대조할 수 있도록 ID를 함께 기록했다.

## 실제 Katakuri 검사와의 대조

별도로 Katakuri 커밋 `c2d8f447ce21`을 임시 디렉터리에 복제하고 위 프로필의 두 검사 명령을 실행했다. 생성기 비교는 오프라인 시험 앱의 `/v1/analytics/execution-performance` 요청이 `403 AUTH_ACCOUNT_SCOPE_NOT_GRANTED`를 반환해 종료 코드 1이었다. 웹 경계 시험도 같은 이유로 생성기 비교 시험 하나가 실패해 **23개 통과, 1개 실패, 1개 생략**이었다. 빌드 출력이 없는 이 복제본에서 프로필이 지정한 정확한 번들 testcase의 관측값은 `skipped`였다. 전체 pytest 프로세스의 실패와 개별 번들 시험의 생략을 각각 확인했다. 이 추가 관측은 위 여섯 번의 대응 평가 집계에서 제외했다.

## 재현

P1 이후 재실행 시 중단 사례는 호출 수를 실제 모델 프로세스 기록과 대조한다.
P0는 구현자 재확인을 포함해 3회, P1은 보존한 파일을 검사와 리뷰에 넘겨 2회다.
위 기준선·변경 후 JSON의 채점기 해시와 수치는 P0 측정 당시의 기록이다.

Git과 pytest가 설치된 Python 3.11 이상에서 저장소 루트를 기준으로 실행한다. 기록한 환경은 Python 3.12.3, pytest 9.0.2다. 기존 작업 원장, 모델 로그인, Katakuri 저장소는 필요하지 않다. 두 실행에서 동일한 Python을 선택한다.

```bash
python3 -m pytest --version
p0_replay=$(mktemp -d)
mkdir "$p0_replay/before"
git archive 9b0c443da3e72fc490ed487289b5ef62ae0242cf | tar -x -C "$p0_replay/before"
python3 pilots/p0-goal-evidence/evaluate.py --arm baseline \
  --engine "$p0_replay/before" --output "$p0_replay/baseline.json"
python3 pilots/p0-goal-evidence/evaluate.py --arm candidate \
  --engine . --output "$p0_replay/after.json"
```

기준선 명령은 측정 결과를 저장하면 종료 코드 0을 반환한다. 변경 후 명령은 기대 결과 또는 검사 참조 검증이 실패하면 종료 코드 1을 반환한다. 각 보고서의 `evaluator_sha256`과 대응 변형의 `fixture_commit`이 일치하는지 확인할 수 있다. 실제 시도마다 검사 ID는 새로 생긴다.

두 실행의 검사 명령은 같다. 이전 버전의 pytest 명령에도 동일하게 JUnit 출력 인자를 넣어 실제로 생략된 시험을 독립적으로 읽을 수 있게 했다. 변경 후 실행은 배포할 [웹 fixture 프로필](../../profiles/katakuri-web-fixtures.json)의 조건 연결 규칙을 읽는다. 검사기·모델 대역·작업 데이터·독립 판정 기준은 두 실행에서 공유한다. 이 평가는 한 프로필의 제어기 결정을 재현하며, 실제 웹 번들 빌드나 실제 모델의 검토 능력을 측정하는 실험은 별도로 수행해야 한다.
