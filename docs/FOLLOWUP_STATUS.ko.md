## 2026-11-27 릴리즈 노트 · AI에게 맡긴 일을 확인하고 이어가기

AI에게 일을 맡기고 나면 세 가지가 궁금합니다. 정말 끝났을까? 중간에 멈췄다면 다음엔 뭘 해야 할까? 지금은 무엇을 하고 있을까? **원장**은 그 답을 적어 두는 작업 기록이고, **관제실**은 그 기록을 보는 화면입니다.

### 일이 끝났는지 확인하기

- **무엇을 검사했는지 볼 수 있습니다.** 다른 도구와 공개 연구를 살펴보고, 먼저 완료 표시를 믿을 수 있게 하는 일을 골랐습니다. 한 작업 유형에서 완료 조건마다 실제 검사 결과를 붙였습니다. 필수 검사를 건너뛴 경우, 파일을 쓴 뒤 멈춘 경우, 사람이 줄 자료를 기다린 경우, 나중 수정으로 앞의 작업이 깨진 경우를 전후로 비교했습니다. 시험에서 잘못 완료로 표시한 일이 1건에서 0건으로 줄었습니다. [설계 조사](HARNESS_STRATEGY_2026-11-26.ko.md) · [완료 판정 실험](../pilots/p0-goal-evidence/README.md)
- **AI를 한 명 더 부를 때 얻는 것도 재 봤습니다.** 작은 변경 다섯 건에서 두 번째 AI의 검사 추천은 문제를 더 찾지 못했고, 요청 5번과 약 53초가 들었습니다. 별도의 AI가 코드를 직접 읽고 살피자 검사가 놓친 문제를 하나 찾았습니다. 정상 변경 두 건을 잘못 막은 일은 없었습니다. 이 수치는 시험한 다섯 건에서 나온 결과입니다. [모델 비교 실험](../pilots/p1-second-model/README.md)

### 멈춘 일을 이어가기

- **이미 한 일을 기억합니다.** 파일을 쓴 뒤 멈췄을 때는 남은 검사를 시작하고, 검사까지 통과했다면 검토부터 합니다. GitHub에서 변경을 올리거나 합친 뒤 답이 오지 않았을 때는 이미 처리됐는지 먼저 확인합니다. 배포됐는지 모를 때도 적용된 버전을 찾아보고, 확인할 방법이 없으면 기다립니다. 네 가지 상황을 시험해 쓰기와 배포가 중복되지 않는 것을 확인했습니다. [중단 복구 실험](../pilots/p1-recovery/README.md)
- **사람과 다음 AI가 같은 기록을 봅니다.** 목표, 남은 일, 지금도 쓸 수 있는 검사 결과, 다음 행동을 같은 원장에서 가져옵니다. 예전 방식과 새 방식 모두 여섯 가지 상황에서 올바른 다음 일을 골랐습니다. 걸린 시간은 비슷했고, 새 방식은 원본 기록을 한 번 덜 열었습니다. [인계 비교 실험](../pilots/p1-handoff/README.md)
- **다른 프로젝트에도 쓸 수 있습니다.** Katakuri와 같은 방식으로 `agent-workflow` 자체의 작은 변경을 등록해 검사와 별도 검토를 거쳐 완료했습니다. 기존 Katakuri 작업도 같은 번호로 이어서 끝냈고, 파일과 운영에 대한 제한을 확인했습니다. 이 변경들을 독립적으로 검토하고 다시 시험한 뒤 기본 버전인 `main`에 합쳤습니다. [두 프로젝트 검증](../pilots/p2-goal-mode/README.md) · [PR #20](https://github.com/89sooner/agent-workflow/pull/20)

### 실제 OpenCode 작업을 화면에서 보기

- **가끔 실패하던 화면 검사를 고쳤습니다.** 처음 연결할 때 인증 안내가 뜨는 검사에서, 지시를 다 쓰기 전에 서버가 빈 파일을 읽고 지울 수 있었습니다. 다 쓴 지시만 보이게 바꿨습니다. OpenCode 검사에도 같은 수정을 하고, 복구 지시가 서버에 실제로 적용됐는지 확인하게 했습니다. 같은 지연을 넣어 고치기 전후를 반복해서 비교했습니다. [온보딩 #21](https://github.com/89sooner/agent-workflow/pull/21) · [OpenCode 검사 #22](https://github.com/89sooner/agent-workflow/pull/22)
- **OpenCode를 켜고 새 일이 생기면 화면에 나타납니다.** 자동 검사에서 실제 OpenCode 1.3.17과 2.2.7을 각각 띄워 확인했습니다. 로컬 8776에서도 AI가 파일 두 개를 읽는 동안 `실행 중`, 끝난 뒤 `대기`가 표시됐습니다. 화면에 나온 모델 `openai/gpt-5.4`와 읽기 두 번의 기록도 OpenCode가 알려 준 값과 일치했습니다. [실제 버전 지원 #23](https://github.com/89sooner/agent-workflow/pull/23)
- **접속 번호와 비밀번호가 바뀌어도 같은 연결을 찾습니다.** OpenCode가 바뀐 접속 정보를 관제실이 다시 읽게 했습니다. GitHub 자동 검사와 실제 로컬 8776에서, 같은 연결 번호로 새 작업이 새로고침 없이 나타나는 것을 확인했습니다. 실제 검증을 마친 뒤 접속 설정을 원래대로 돌렸고, 기존 원장 두 개도 그대로 열렸습니다. [자동 재연결 #24](https://github.com/89sooner/agent-workflow/pull/24) · [실제 검증 결과와 따라 하는 순서](OPERATIONS.ko.md#opencode-live-rotation)

## 지금 바로 쓸 수 있는 범위

목표와 완료 조건을 정한 뒤 등록한 프로필을 선택한다. 도구가 별도 폴더에서 구현과 검사,
독립 리뷰, 인계를 연결한다. 설정한 횟수와 시간의 범위를 넘으면 중단 이유를 남긴다.
프로젝트와 작업의 적절성은 사용자 또는 대화 중인 에이전트가 판단한다.

## 외부 대상이 정해졌을 때 연결할 범위

1. 실제 Git 호스트와 저장소, 기준 브랜치를 확인한다.
2. 배포할 프로그램과 적용 버전을 확인할 명령을 정한다.
3. 대상 프로젝트의 배포 실패 복구 절차를 정한다.
4. 알림이 필요하면 실제 수신 채널과 사용할 명령을 정한다.
5. 지정한 대상으로 릴리스와 상태 확인을 한 번 검증한다.

사용자는 현재 외부 대상을 정하지 않았다고 답했다. 임의의 클라우드 자원이나 계정을
만들지 않았다. 현재 WSL에서의 로컬 실행은 이 결정을 기다리지 않고 사용할 수 있다.
공용 서버의 인증·조직 권한·SSO와 GitLab·Bitbucket 전용 릴리스는 별도 확장이다.

## 완료 표시를 읽는 법

`completed`는 기록 당시의 완료이고 `completion_is_current`는 현재 코드와의 일치다.
지난 `AW-AUTOMATION-001`은 검사 후 직접 커밋하면서 HEAD와 index가 바뀌었다.
따라서 과거 검사 상태를 현재 검사로 표시하지 않는다. 당시 게시 기록은 소스 내용이
같았음을 별도로 확인했다. 이 기록을 무조건 현재로 바꾸거나 완료된 작업을 덮어쓰지 않는다.
이번 `KB-WEB-FIXTURE-R29`는 검증된 worktree를 유지하므로 현재 근거 세 값이 모두 `true`다.
