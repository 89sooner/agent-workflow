# 관제실 사용성·관측 개선 구현 계획

> 상태: baseline (2026-11-05 사용자 순차 구현 지시)
> 작성: 2026-11-05 (Asia/Seoul)
> 기준 소스: `388752203b3bc98eda45b4c4dd60f9ea68ef74bc`
> 범위: 기존 제품의 증분 개선. 본 문서는 계획이며 구현·병합·운영 반영 완료를 뜻하지 않는다.

## 1. 근거와 목표

근거는 [유사 앱 조사](SIMILAR_APPS_RESEARCH_2026-11-05.ko.md)와 현재 소스다. 기존 [사용성 계획](USABILITY_SERVICE_PLAN.ko.html)의 구현 이력은 유지하며, 이번 후속 범위와 충돌하면 현재 사용법·소스 사실을 먼저 확인한다. 조사 아이템은 후보이며 아래 릴리스 범위와 수용 기준을 통해 구현 단위로 구체화한다.

주 사용자는 OpenCode·Claude Code·Codex로 일상 개발을 하는 사내 개발자다. WP 없이 관측할 수 있어야 하며 기존 WP 실행·검사·리뷰·이력 기능도 접근 가능해야 한다.

목표 흐름: 한 URL 접속 → 프로젝트 발견·연결 → 첫 이벤트 확인 → 작업 상태 관측 → 질문·승인 대기 알림 → 원래 작업으로 복귀 → 결과·근거 확인.

성공 기준: 포트·state home을 모르는 사용자도 연결을 완료하고, 관측 실패 원인과 사람이 개입할 세션을 찾는다. 3D 움직임은 수신된 활동의 의미를 전달한다.

## 2. 범위와 용어

- 관측 소스(source): 등록된 workflow 원장, OpenCode API 연결 또는 프로젝트 훅/플러그인 등록.
- 프로젝트(project): Git 공통 디렉터리를 기준으로 묶는 작업 공간. worktree별 경로는 별도 보존한다.
- 세션(session): 공급자·소스·native ID로 식별하는 일상 대화 실행. workflow task/run과 별도 엔터티다.
- 확인 요청(attention): 질문·권한 대기로 관측된 상태. 세션 응답 종료와 작업 검증 완료는 별개다.
- 신선도(freshness): 마지막 관측 시각으로 판단하는 데이터 유효성. 연결 정상과 실행 중의 증거를 구분한다.

| 릴리스 | 범위 | 조사 대응 |
|---|---|---|
| REL-01 | 관측 계약·신선도, 통합 진입점, 발견·연결 진단, 확인 요청 정렬·알림 | P0-1~5, P1-2 |
| REL-02 | 복귀 안내, 부모·자식 트리, 실제 활동별 3D, 프로젝트 구역, 결과 연결 | P1-1, P1-3~6 |
| REL-03 | 북마크·구간 내보내기, 관측 시간·도구 오류 분석 | P2-1~2 |
| REL-04 조건부 | 토큰·비용 추적 | P2-3; 공급 데이터와 가격 기준 확정 후 착수 |

제외: 사내 SSO·팀 권한, 임의 대화 전문 일괄 수집, 에이전트에 자동 응답·승인, 범용 IDE·원격 터미널 재구축, 실행 엔진 교체, 외부 앱 코드 복제. 8765는 본 작업의 운영 관리 대상이 아니다.

단일 URL은 관측 화면·소스 연결의 통합을 뜻한다. DB 병합이나 큐 실행 서버 제거를 전제하지 않는다. 관측 전용 진입점은 `watch` 모드로 구성하고 기존 관리 기능은 명시적인 관리 경로로 연결한다.

## 5. 기술 설계 방향

React·TypeScript·R3F, Python 표준 라이브러리 서버, SQLite와 패키지 내 정적 자산을 유지한다. Next.js·별도 모델 프록시 도입은 이 계획의 전제 조건이 아니다.

- 프런트: `frontend/mission/App.tsx`, `NativeSessions.tsx`, `Connections.tsx`, `Room.tsx`에 공통 프로젝트 선택·상태 모델을 연결한다. 서버 상태와 로컬 UI/알림 설정을 분리한다.
- 백엔드: `connections.py`는 후보와 프로젝트 식별, `onboarding.py`는 연결 권한·설정, `native.py`는 수집·세션·신선도, `server.py`는 API 경계를 담당한다. 집계 실패는 소스별 격리한다.
- 식별: workflow는 ledger_id+task_id+run_id, native는 provider+source+native_id. raw ID 단독 join 금지. managed/native 레코드를 무리하게 같은 task로 변환하지 않는다.
- 데이터: `native-observation.sqlite3`에 필요한 전이 ID·대기 시작·활동 종류를 추가한다. 기존 500세션·10,000이벤트·200선택 이력 한도를 기본 유지하고 확대는 측정 후 결정한다.
- 북마크 등 사용자 메타데이터는 관측 home 소유 저장소에 분리한다. 외부 원장에 쓰지 않는다. 마이그레이션 버전·트랜잭션·백업 복원 검증을 포함한다.
- API 후보: `/api/overview`, `/api/connections/diagnostics`, `/api/attention`, `/api/bookmarks`. 기존 API는 호환 유지. 실제 path·DTO·권한은 WP-OBS-01에서 계약 문서로 고정한다.
- 연결 저장은 기존 CSRF·origin·capabilities 검사를 재사용한다. 진단 GET은 설치나 등록을 수행하지 않는다. 의도적인 설정 쓰기는 별도 POST다.
- 알림은 브라우저 Notifications와 인앱 표시부터 시작한다. 브라우저가 닫힌 상태의 알림은 제외한다. 동일 origin 다중 탭은 전이 ID 기반 리더 선출·중복 방지, 다른 origin 간 중복 억제는 범위 밖으로 명시한다.
- 3D는 동일 세션 모델을 사용하며 서버에 없는 의미를 생성하지 않는다. 목록 보기는 3D 없이도 모든 핵심 관측 정보를 제공한다.

## 7. 검증·출시 게이트

각 릴리스는 다음 증거를 모두 갖춘 뒤 완료로 표시한다.

1. FR별 코드·테스트·스크린샷·호스트 버전·SHA를 아래 실행 원장에 기록한다.
2. Python 검사, 프런트 typecheck/build, 영향을 받는 기존 mission·native·연결 브라우저 회귀를 통과한다.
3. 실제 Chromium에서 최초 연결·세션 선택·대기 전이·오류 복구·390px 화면·키보드 흐름을 검증한다. synthetic 증거와 실제 호스트 이벤트를 구분한다.
4. 세 도구의 테스트 프로젝트에서 첫 이벤트·하위 세션·종료를 실제 지원 범위만큼 확인한다. 검증하지 못한 공급자는 그 기능의 완료 범위에서 제외하고 이유를 공개한다.
5. 사내 파일럿 목표: 신규 사용자 3명 중 3명이 도움 없이 프로젝트 연결·첫 세션 관측을 10분 안에 완료하고, 제공된 확인 요청을 30초 안에 찾는다. 목표 미달 시 막힌 단계를 수정하고 재검증한다. 실제 사용자 참여 전에는 충족했다고 보고하지 않는다.
6. 변경분 독립 리뷰와 매뉴얼 최신화를 마친다. 운영 반영 전 백업·복구·모드별 권한 검증을 완료한다.

### 개발·운영 보존

- 구현은 `codex/observatory-usability-*` 별도 브랜치·격리 worktree·전용 state home·비운영 포트에서 진행한다. 운영 소스 checkout에서 개발 서버·fixture를 실행하지 않는다.
- 로컬 소스 pull도 정적 자산을 바꿀 수 있으므로 운영 반영 시점에 수행한다. 기존 수정·증거·개발 worktree는 보존한다.
- 운영 통합은 REL-01 이후 별도 단계다. 8776/8777의 연결·권한·jobs·batches·직접 실행을 확인하고 worker 없는 관측 진입점에서 두 원장 접근을 검증한 뒤 기본 URL을 전환한다. 하나를 종료하는 것은 데이터 접근·관리 기능 대체가 입증된 뒤 결정한다.
- 큐 worker가 있는 서버 재시작은 작업 상태를 먼저 확인한다. 관측 UI 배포가 worker 실행을 유발하지 않는 방식을 우선한다. 운영 원장 DB 병합은 하지 않는다.
- 롤백: 이전 코드·정적 자산·관측 home 백업으로 복구하고 기존 URL 유지. 외부 원장에 쓴 변경이 없어야 한다. 실제 복원 리허설과 소요 시간을 기록한다.
- 초기 계획 작성 후 사용자의 순차 구현 지시로 별도 개발 브랜치에서 구현 중이다. 운영 반영·프로세스 변경은 별도 검증 단계로 남긴다.
