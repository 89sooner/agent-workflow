# 프로젝트 연결과 실제 에이전트 관제실

이 기능은 `feat/project-observatory-ux` 브랜치에만 구현한다. 운영 checkout,
기존 서버, 원장을 교체하거나 origin/main에 병합하는 절차는 포함하지 않는다.
`completed`와 프로세스 정상 종료, 실제 배포는 서로 다른 증거다.

## 먼저 관측하기

새 브랜치 소스에서 다음처럼 실행한다. 설치된 운영 `agent-workflow` 명령은
이번 브랜치의 새 명령을 제공하지 않을 수 있다.

```bash
cd /tmp/agent-workflow-project-observatory-20261101
/home/roqkf/.pyenv/versions/3.12.3/bin/python3 -m agent_workflow \
  --home /tmp/my-workflow-observer watch --port 8878
```

`watch`는 조회 전용 서버만 시작한다. 큐 worker, 모델 호출, 작업 재개,
관측 대상 DB의 생성·마이그레이션을 하지 않는다. 서버의 잠금과 메타데이터는
지정한 observer home에만 기록한다. 원장이 없어도 빈 연결 화면을 제공한다.
운영 8765·8776·8777을 종료해서 포트를 확보하지 않는다.

발견 대상은 기본 상태 경로, 저장된 연결, `agent-workflow --home` 또는
`python -m agent_workflow --home` 프로세스 인자, `/tmp/*workflow*/state.sqlite3`의
제한된 후보다. 사용자 홈 전체나 대화 로그는 탐색하지 않는다. Docker 운영
제어 서버나 shell 명령 문자열을 에이전트로 인식하지 않는다. 목록은 최대
15초간 캐시하며 화면은 보이는 동안 4초마다 갱신한다.

왼쪽 **작업 원장 선택**에서 최근 작업이 있는 원장을 선택한다. 프로젝트
전체 관제실이 기본 화면이다. 에이전트나 작업을 선택하면 개별 실행의 단계,
이벤트, 이전 실행, 기록 재생으로 이동한다. **프로젝트 전체 보기**로 돌아온다.
조회 전용 상태에서는 등록·실행·중단 버튼과 모든 POST 요청이 차단된다.

`serve --read-only`는 지정한 기존 DB와 저장한 연결만 읽는다. `watch`와 달리
프로세스·임시 경로의 자동 발견을 추가하지 않는다. 기존 일반 `serve`는 여전히
worker를 함께 시작하므로 관측만 하려면 `watch` 또는 `serve --read-only`를 쓴다.

## 연결을 기억하고 등록 간소화하기

다음 명령은 기능 사용법 예시다. 운영 원장에 실제 등록하기 전에는 사용할
프로젝트, 원장, 검사 정책이 현재 사용자의 작업 범위인지 확인한다.

1. 별도 observer home을 정한다. 두 번째 명령부터 같은 환경변수를 사용하면
   `--home`을 반복할 필요가 없다.

   ```bash
   export AGENT_WORKFLOW_HOME=/tmp/my-workflow-observer
   ```

2. 프로젝트를 연결한다. 연결은 관측 정보만 저장하며 작업을 실행하지 않는다.

   ```bash
   python3 -m agent_workflow connect /path/to/katakuri-band \
     --ledger /path/to/existing-workflow-state
   ```

3. 이미 승인한 프로젝트 프로필이 있으면 이름과 공통 완료 조건을 기억시킨다.
   프로필에 등록한 검사 명령·허용 경로·격리 정책을 그대로 사용한다. 저장소의
   임의 설정이나 문장으로 실행 권한을 새로 추론하지 않는다.

   ```bash
   python3 -m agent_workflow connect /path/to/katakuri-band \
     --ledger /path/to/existing-workflow-state --profile trusted-profile \
     --criterion '요청 동작을 구현하고 등록된 필수 검사를 통과한다'
   ```

4. 이후 해당 프로젝트 위치에서 목표와 이름만으로 작업을 등록한다. 작업 ID는
   자동 생성한다. 추가 조건은 `--criterion`으로 명시한다.

   ```bash
   python3 -m agent_workflow start '주문 타임라인의 빈 상태를 개선한다' \
     --project /path/to/katakuri-band \
     --name '주문 UI 담당' --reviewer-name '주문 검토 담당'
   ```

   **`start`는 등록만 한다.** 모델이나 큐를 시작하지 않는다. 반환된
   `state_home`, `task.id`, `task_key`가 실제 연결 정보다. 복수 원장이 있으면
   `connect --registration-home PATH`로 등록 대상을 하나로 정해야 한다.
   사라진 기존 원장은 빈 DB로 대체하지 않는다. 프로필이 없는 등록은 검사와
   격리 정책도 자동으로 생기지 않으므로 이를 명시적으로 준비해야 한다.

5. 반환된 실제 state home과 ID로 `show`, `brief`를 실행해 작업 계약과 현재
   코드 상태를 확인한다. 기존 대화형 세션을 활용할 경우 아래 프롬프트를
   담당 에이전트에게 전달한다. 이 문서나 UI가 프롬프트를 자동 전송하지 않는다.

   ```text
   현재 요청: [승인된 구체적인 목표]
   프로젝트: [해당 작업의 실제 격리 worktree 경로]
   원장: [start가 반환한 state_home]
   작업 ID: [start가 반환한 task.id]
   담당 이름: [등록한 이름]

   agent-workflow show로 이 작업의 목표·허용 범위·검사·현재 Git 상태를 확인하라.
   같은 목표의 작업을 중복 등록하지 말고 이 ID로 이어서 진행하라.
   운영 checkout·운영 서버·다른 에이전트 파일은 수정하지 말라.
   승인되지 않은 병합·배포·추가 작업을 시작하지 말라.
   진행 상태와 실제 결과는 checkpoint에 남기고, 지정 검사를 실행하라.
   작업 완료와 검사 통과, 독립 리뷰, 병합·배포 상태를 구분해서 보고하라.
   ```

6. 병렬 작업은 각자 다른 작업 ID와 격리 worktree, 구체적인 허용 경로를
   사용한다. 공통 파일 변경은 한 담당자에게 맡긴다. 작업 등록은 병렬 실행을
   자동 승인하지 않는다. 승인한 작업만 기존 `run`/`queue`/batch 정책으로
   실행한다. 기존 직접 실행을 관제실에 나타내려고 다시 실행하지 않는다.

7. 관제실의 **실행 중**은 큐 job과 연결된 run을 한 건으로 묶으며 직접 run도
   포함한다. 프로세스 식별자가 확인되지 않으면 **상태 미확인**이다. 대화형
   세션이 checkpoint만 기록했다면 구현 단계의 세부 활동은 관측되지 않는다.

## 이름·움직임·이력의 의미

- 에이전트의 ID는 provider 이름이 아니라 각 실행 invocation의 안정적인 ID다.
  동일 공급자·동일 표시 이름이어도 별개의 실행을 합치지 않는다.
- `start --name`, 웹 등록 폼의 이름은 명시적 할당 이름이다. 새 실행 시작 시
  기록에 복사되므로 이후 이름을 바꿔도 과거 실행 이름이 변하지 않는다.
- 옛 기록에 이름이 없으면 공급자·역할·작업 ID로 생성하고 **자동 이름**으로
  표시한다. 과거 H 작업에 실제로 기록되지 않은 사람 이름을 만들어 넣지 않는다.
- 요청 모델과 실제 관측 모델은 구별한다. 네이티브 session ID가 없으면 비워 둔다.
  프로세스 생존은 모델이 추론 중이거나 특정 도구를 사용 중이라는 뜻이 아니다.
- 실행 중 상태는 손·머리·모니터의 활동으로 표현한다. 새로운 프로세스 지시와
  결과 반환 이벤트에는 한 번만 전달 움직임을 보여 준다. 첫 화면의 옛 이벤트는
  재생하지 않는다. 연결이 끊기거나 상태가 미확인이면 활동을 멈춘다.
- 카메라·선택은 갱신 때 유지한다. **최신 단계 따라가기**를 켜면 새 단계로
  이동한다. 기록 재생은 과거 관측이며 작업을 실행하지 않는다.
- 3D에는 선택·실행 중 에이전트를 우선해 최대 8개를 표시한다. 전체 대상은
  에이전트 목록과 작업 목록으로 탐색한다. 완료 프로젝트는 최근 실행을 보여 준다.
- 화면이 숨겨지면 연속 렌더링을 멈춘다. 움직임 줄이기와 WebGL 대체 목록도 지원한다.

## 구현 경계

원장은 ID로 구분하며 같은 task ID가 다른 DB에 있어도 혼동하지 않는다.
현재 UI는 원장을 선택해 관측한다. 여러 원장의 모든 작업을 하나의 실행
대기열로 합치거나 서로 다른 controller를 제어하지 않는다. Git common-dir이
같은 worktree는 같은 프로젝트로 묶지만, 삭제된 작업 경로나 별개 clone은
증거 없이 같은 프로젝트라고 추정하지 않는다.

외부 Codex/Claude의 임의 대화 로그 파싱, 자동 프롬프트 전송, 네이티브 하위
에이전트 자동 연결, SSE 전송은 이번 구현에 포함하지 않는다. 해당 제공자의
검증된 이벤트 인터페이스와 실제 session ID 연동은 별도 단계다. 현재는 기존
agent-workflow가 기록한 실행과 명시적 연결을 자동 발견한다.

## 개발 격리 검증

운영 checkout의 미커밋 변경은 새 worktree로 복사해 보존했다. 회귀 검사는
임시 Git 저장소·DB·합성 모델 fixture에서 실행한다. 최근 H 조회 검증은 원장의
SQLite backup 복사본을 사용한다. 미리보기는 스냅샷이며 실시간 운영 원장과
다를 수 있다. 운영 코드, 모델 작업, 원격 main은 이 검증으로 변경하지 않는다.
