# agent-workflow의 다음 설계

2026년 11월 26일 · 조사 기준 커밋 `9b0c443da3e7` · 외부 1차 자료 44건

**첫 투자로 권하는 것은 완료 판정을 시험하는 작은 평가 세트다. 첫 제품 변경으로는 완료 조건을 실제 검사 결과에 연결하는 기능을 권한다.** 지금도 이 시스템은 Claude가 만든 변경을 Codex에 넘기고, 등록한 검사를 실행하고, 코드가 달라지면 과거 증거를 무효화한다. 남아 있는 비싼 질문은 “검사가 통과한 이 변경이 사용자가 요청한 행동을 정말 제공하는가?”, “내일 다른 세션에서 무엇을 다시 해야 하는가?”다. 이 두 질문을 몇 분 안에 답하게 만드는 것이 로컬 도구로서의 경쟁력이다.

## 1. 저장소가 이미 보여 주는 것

| 확인한 동작 | 발전 방향을 정할 때의 의미 |
|---|---|
| 완료 시 HEAD, index, 무시되지 않은 작업 파일과 참조 문서를 확인한다. 실제 검사 기록이 필요하고, 리뷰어가 지정된 작업은 현재 지문의 리뷰도 필요하다. | 코드 신선도를 판정하는 기반은 갖췄다. 그 위에서 **무슨 행동을 입증했는지** 표현할 수 있다. [완료 판정](../agent_workflow/core.py) · [실제 검사·리뷰](../agent_workflow/runner.py) |
| Katakuri는 조건을 계획하거나 받아서 진행하고, 외부 입력이 필요한 조건을 대기시키며, 나머지는 계속한다. 조건 전체에 대한 독립 리뷰, 호출·시간·보고 토큰 예산, 입력 지문에 따른 검사 재사용이 있다. | 장기 목표 루프를 새로 만들 필요가 작다. 일반화하기 전에 어떤 계약이 Katakuri 전용인지 분리할 수 있다. [목표 실행기](../agent_workflow/katakuri_goal.py) · [운영 계약](KATAKURI_GOAL.ko.md) |
| 조건별 리뷰의 `criterion`, `accepted`, `evidence`를 검사한다. 조건 누락·중복·종합판정 불일치는 거부한다. `evidence`는 비어 있지 않은 설명 문자열이고, 작업 단위 검사는 별도로 집행된다. | 리뷰 문장을 읽으면 이유를 알 수 있다. 특정 조건을 어떤 검사 실행이나 산출물이 뒷받침하는지 기계적으로 역추적하는 데는 추가 연결이 필요하다. [read_coverage와 run](../agent_workflow/katakuri_goal.py) |
| 검사 추천은 사람이 표시한 기대 묶음과 대조한다. 자동 보조 리뷰는 같은 프로필·입력 특성의 최근 최대 10건을 보고, 비교 가능한 라벨이 5건 미만이면 기존 규칙을 쓴다. 잘린 입력은 별도 처리한다. | 이미 두 번째 모델이 구한 검사와 불필요하게 추가한 검사를 계산한다. 다음 측정 대상은 **추천에서 빠진 검사가 실제로 잡았을 회귀**다. 이 라우팅은 검사 추천용이며 최종 코드 리뷰와 역할이 다르다. [라우팅 규칙](../agent_workflow/reviewer_policy.py) · [추천 관측 기록](../agent_workflow/recommendation_records.py) |
| 데몬 재시작 시 실행 중이던 작업은 중단으로 기록한다. 릴리스는 커밋 전 의도를 저장하고, 같은 SHA의 PR을 찾아 재사용하고, 결과가 불명확한 배포는 명시적 재시도를 요구한다. | 복구의 기본 메커니즘이 있다. 다음 가치는 중단된 **각 단계에서 이미 반영된 효과와 계속할 수 있는 행동**을 일관되게 설명하는 데 있다. [데몬](../agent_workflow/daemon.py) · [릴리스](../agent_workflow/release.py) |
| 일상 세션의 `pickup`에는 현재 증거 상태가 있고, 수동 재개와 pickup의 소요 시간·잘못 고른 작업·다시 설명한 횟수를 측정할 수 있다. 관제실에는 실행 구간, 알림, 세션별 근거가 있다. | 새 대시보드를 만드는 비용 없이, 인계의 첫 화면과 첫 행동을 개선한 효과를 측정할 수 있다. [세션 인계](../agent_workflow/session_notes.py) · [재개 측정](../agent_workflow/resume_metrics.py) · [관제실 안내](OBSERVATORY_REL01_USAGE.ko.md) |

### 같은 ‘완료’ 속에 다른 두 결과가 있다

- 두 사례는 같은 프로젝트에서 선정한 과거 작업이다. 신규 사용자 3명 파일럿은 미실시로 기록돼 있고 PR Search 파일럿은 철회됐다. 따라서 현재 자료로는 타 프로젝트 전이성, 최초 사용성, 평균 절약 시간, 무인 성공률을 추정하기 어렵다. [신규 사용자 파일럿](../pilots/READINESS_PILOT.ko.md) · [철회 기록](../pilots/PRS-WP061/WITHDRAWN.md)

## 2. 유사 시스템에서 가져올 설계

유사성은 같은 문제를 얼마나 직접 다루는지로 보았다. **목표를 여러 세션에 걸쳐 끝내는 문제에는 Factory Missions**, **작업을 배정하고 현실과 상태를 맞추는 문제에는 Symphony**, **여러 로컬 코딩 에이전트를 감독하는 사용 경험에는 Agent Orchestrator와 Vibe Kanban**이 가까웠다.

| 시스템 | 원자료에서 확인한 설계 | agent-workflow에 적용할 판단 |
|---|---|---|
| Factory Missions | 기능 목록 작성 전에 관찰 가능한 행동으로 검증 계약을 만든다. 각 기능이 담당할 조건을 지정하고 마일스톤이 끝나면 새 에이전트가 검사한다. | 자동 분해가 원래 목표에서 조건을 빠뜨렸는지 점검하고, 각 조건에 허용할 증거 종류를 먼저 정한다. [Factory 설계 설명](https://factory.com/news/missions-architecture) |
| OpenAI Symphony | 저장소의 `WORKFLOW.md`, 이슈별 작업공간, 스케줄링·재시도·트래커 상태 재조정을 명세한다. 공개 명세는 Draft v1이다. | 기존 프로필에 정책 버전을 고정하고, 재개 직전에 외부 상태를 대조하는 규칙을 문서화한다. 이 패턴은 로컬 SQLite에서도 쓸 수 있다. [서비스 명세](https://github.com/openai/symphony/blob/main/SPEC.md) |
| Stripe Minions | 모델이 판단하는 작업 사이에 Git, 린트, 테스트 같은 결정적 단계를 둔다. Stripe 개발 환경을 전제로 한 운영 사례다. | 실행기가 이미 소유한 검사·완료 경계를 활용한다. 반복해서 발생하는 모델 판단 하나를 실행 가능한 검사 하나로 바꾸는 투자의 효과를 측정한다. [Stripe 엔지니어링](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents) |
| Claude Ship | 2026년 11월 23일 발표한 베타다. PR 검토, 실패한 CI·리뷰 의견을 처리하는 PR Steward, 팀 정책에 따른 승인 판단을 나눈다. 승인 판단은 관찰 전용으로 시험할 수 있다. | PR 자동 수정 자체는 이미 공급자 제품과 겹친다. 외부 PR 결과를 로컬 조건의 증거로 수입하고 새 판정 규칙을 관찰 모드에서 비교하는 쪽이 유망하다. [공식 발표](https://claude.com/resources/articles/introducing-claude-ship) |
| Agent Orchestrator | 로컬에서 작업마다 에이전트·브랜치·worktree를 두고 CI와 리뷰 상태를 감독한다. | 작업 목록에서 사람이 개입할 한 건을 누르면 문제의 검사·변경·다음 행동으로 바로 이어지게 한다. [공식 저장소](https://github.com/OrchestratorInc/agent-orchestrator) |
| Vibe Kanban · Conductor | Vibe Kanban은 이슈에서 여러 저장소의 worktree를 준비하고 변경 검토와 실행 확인으로 연결한다. Conductor도 격리된 workspace에서 병렬 에이전트를 운영한다. | 추가 병렬 실행을 설계할 때 사용자 편익을 ‘동시에 시작한 수’와 ‘검토하고 통합하는 데 든 시간’ 양쪽에서 측정한다. [Vibe Kanban 사용 흐름](https://github.com/BloopAI/vibe-kanban/blob/main/docs/getting-started.mdx) · [Conductor 병렬 작업](https://www.conductor.build/docs/concepts/parallel-agents) |

| OpenHands Software Agent SDK | 모델 라우팅, 실행 환경, 생명주기, 사용자 인터페이스를 나누고 실행 이벤트를 보존한다. 저자들은 운영 자료로 시스템 기인 실패도 평가했다. | 모델 오답과 하네스 장애를 별개로 집계한다. 공급자 확장 수요가 생기면 기능별 계약 테스트부터 만든다. [MLSys 2026 논문](https://proceedings.mlsys.org/paper_files/paper/2026/hash/8ae9cf363ea625161f885b798c1f1f78-Abstract-Conference.html) |
| GitHub Copilot cloud agent · GitHub Agentic Workflows | 전자는 브랜치와 PR 권한을 제한하고, 후자는 모델이 요청한 쓰기 작업을 사전에 허용한 출력 경로에서 집행한다. | 일반 목표 프로필에서도 관측, 로컬 쓰기, 검증, 외부 반영 권한의 주체를 명확히 한다. 네이티브 세션 관측 이벤트는 조사 자료로 연결한다. [Copilot 권한 경계](https://docs.github.com/en/copilot/concepts/security-governance-and-network-settings/risks-and-mitigations) · [Safe Outputs](https://github.github.com/gh-aw/reference/safe-outputs/) |

## 3. 연구가 바꾸는 설계 결정

| 결정 | 연구에서 관찰한 것 | 여기서 검증할 가설 |
|---|---|---|
| 완료한 조건도 나중에 다시 깨질 수 있다 | LoopsBench는 실제 출처의 112개 작업을 검증 가능한 단위와 선행관계로 나누고 이전 단위의 테스트를 회귀 의무로 남겼다. SWE-CI는 100개 작업에서 저장소가 여러 차례 바뀌는 과정을 평가했다. RoadmapBench는 여러 요구가 있는 실제 버전 업그레이드 115건을 다뤘다. | 다음 조건의 구현이 앞선 조건을 깨뜨리는 2단계 사례를 추가한다. 최종 지문에서 모든 필수 행동이 여전히 성립해야 한다. [LoopsBench](https://arxiv.org/abs/2608.00267) · [SWE-CI](https://arxiv.org/abs/2603.03823) · [RoadmapBench](https://arxiv.org/abs/2605.15846) |
| 하네스 결함과 모델 편차는 다른 실험이 필요하다 | Doc2Harness는 고정된 모의 모델로 요청, 파일, 종료 코드, 명령 출력을 검사하고 항상 실패하는 구현도 걸러내는 대조군을 둔다. τ-bench는 대화가 끝난 뒤 환경 상태를 확인하고, 같은 작업에서 일관되게 성공하는지 측정한다. | 제어기 계약은 반복 가능한 fixture로, 모델을 포함한 사용자 작업은 새 worktree에서 여러 번 실행해 측정한다. 공급자 장애도 별도 결과로 집계한다. ## 4. 구현 우선순위

### P0 · 완료 판정을 반증할 수 있는 평가 세트

**첫 변경 단위는 로컬에서 반복 가능한 사례 네 개다.** 과거 파일럿의 실제 운영 환경을 복구할 필요 없이, 같은 의사결정이 필요한 작은 Git fixture를 만든다. 각 사례에 시작 커밋, 사용자 요청, 기대 행동, 허용된 중단 사유, 독립 채점기를 붙인다. 작업 중 에이전트가 수정할 수 있는 경로 밖에 채점기를 두고, 정상 해법이 실제로 통과하는지도 시험한다.

| 사례 | 외부에서 관찰할 정답 | 잡고 싶은 오류 |
|---|---|---|
| R29형 fixture 수정 | 지정한 fixture가 새 생성 결과와 일치하고 관련 없는 필드는 보존된다. 번들 준비 여부는 별도 값이다. | 일부 시험이 생략됐는데 번들까지 확인했다고 결론 냄 |
| 구현 직후 응답 중단 | 파일에 적힌 변경이 보존된다. 기존 증거와 현재 입력에 따라 적절한 검사·검토 단계에서 이어간다. | 같은 변경을 다시 쓰거나 소모된 호출 예산을 되돌림 |

### P0 · 조건별로 ‘무엇이 입증됐는가’를 남기기

지금의 지문 검사는 “같은 코드와 참조인가?”에 답한다. 제안은 등록된 조건에 **사용자가 기대한 행동**, **그 행동을 볼 곳**, **관측 결과**를 붙이는 것이다. 자동 분해된 조건이라면 원래 목표 중 어디에서 나온 것인지도 남긴다. 구현 에이전트가 작성한 설명, 등록된 검사가 생성한 결과, 독립 검토자의 판단, 사용자가 제출한 외부 자료에는 각각 출처를 표시한다.

| 예시 조건 | 사용할 증거 | 판정 예 |
|---|---|---|
| 16개 fixture가 생성기와 일치한다 | 현재 지문에서 실행한 생성기 비교의 결과 ID, 검증된 수량 | 16개 일치가 관측돼 충족 |
| 빌드된 번들이 새 값을 표시한다 | 빌드된 번들을 대상으로 한 전용 검사의 결과 | 번들 미생성으로 미검증. 필수 조건으로 등록한 작업에서만 완료를 보류 |
| 운영자가 외부 관측 자료를 제공한다 | 해당 조건으로 제출한 자료의 해시와 출처, 검토자가 확인한 범위 | 파일 수신과 내용의 타당성 검토를 따로 기록 |

두 번째 행은 설명을 위한 가상 조건이다. 과거 R29에 새로운 필수 조건을 소급하지 않는다. 범용 명령에서는 종료 코드만으로 하위 시험의 skip을 식별하기 어렵다. 첫 구현은 구조화 리포트를 내는 검사 하나에 한정한다.

- **최소 변경**은 목표 모드 한 프로필에서 기존 검사 결과에 안정적인 참조를 붙이고, 조건별 리뷰에 그 참조와 근거 종류를 선택적으로 기록하는 것이다. 컨트롤러는 참조가 해당 작업·현재 지문·검사에 속하는지 확인한다. 주관적 조건에는 관찰 절차와 독립 검토자의 설명을 허용한다. 기존 작업은 기록된 증거 수준으로 읽힌다. [조건별 리뷰](../agent_workflow/katakuri_goal.py) · [검사 결과 저장](../agent_workflow/runner.py)
- **첫 표시 위치**는 작업 상세의 기존 조건 목록이다. 조건을 누르면 원본 검사, 실행 시각, 대상 지문, 필수 여부를 본다. 다른 세션의 모델도 같은 데이터를 읽는다. 장비 간 증거 교환이 필요해지면 대상 digest와 주장 종류를 나누는 in-toto 형식을 참고할 수 있다. 로컬 해시는 작성자의 신원을 인증하지 않는다. [작업 관리 화면](../frontend/mission/Management.tsx) · [in-toto Statement v1](https://github.com/in-toto/attestation/blob/main/spec/v1/statement.md)
- **채택 조건**은 생략된 필수 시험, 다른 지문의 성공, 다른 조건에서 가져온 무관한 결과를 구별하고 정상 대조 사례를 수용하는 것이다. 참조가 유효해도 그 검사가 조건을 의미상 입증하는지는 독립 채점·표본 리뷰로 확인한다. 초기에 기존 판정과 새 판정을 나란히 기록하고 불일치부터 읽는다.

### P1 · 중단 시 마지막으로 확인한 효과에서 재개하기

중단을 만날 때마다 일반적인 ‘다시 실행’을 제공하면, 가장 중요한 판단을 사람이 떠안는다. **중단 이유·확인된 효과·다음에 안전한 행동**을 한 번에 반환하자. 현재 릴리스와 예산 코드에는 이 판단의 상당 부분이 존재한다. 우선 기존 상태를 읽는 진단으로 만들고, 효과를 확정할 수 있는 경로만 자동 재개 후보로 올린다. [릴리스 복구](../agent_workflow/release.py) · [예산 예약과 대조](../agent_workflow/usage.py) · [기존 복구 회귀 시험](../tests/test_release_hardening.py)

| 끊긴 시점 | 다음 행동의 근거 | 수용 조건 |
|---|---|---|
| 구현이 파일을 쓴 뒤 최종 응답 전 | 부분 diff, 범위, 등록 기준, 기존 실행 기록 대조 | 완성 여부를 추정하지 않고 등록 검사 또는 추가 구현을 선택. 중복 구현·예산 초기화 검출 |
| 검사 성공 후 리뷰 전 | 코드·참조·검사 계약·관련 실행 환경이 유효한지 확인 | 유효하면 리뷰로, 바뀌었으면 사유와 다시 필요한 검사 표시 |
| PR 생성·병합의 원격 응답 유실 | 대상 저장소·브랜치·예상 SHA에 맞는 원격 효과 조회 | 같은 PR·병합을 한 번 더 만들지 않고 이미 확인한 결과 연결 |
| 배포 효과 불명 | 대상이 적용된 버전을 조회할 수 있는 경우 그 결과를 읽음 | 결과를 확정할 수 없으면 확인 필요 상태를 보존. 무조건적인 재배포 0건 |

같은 호출이 두 번 전달될 수 있으므로 **재시도해도 되는 작업, 외부 결과를 먼저 조회할 작업, 운영자가 확인할 작업을 구별하는 기록**이 필요하다. 실행 환경이 결과에 영향을 주는 검사에는 검증기 버전·관련 의존성 또는 fixture digest를 선택적으로 묶는다. 코드가 그대로여도 검증기가 바뀌면 예전 성공의 의미가 달라질 수 있다. [Temporal](https://docs.temporal.io/activity-definition) · [Restate](https://restate.dev/blog/why-we-built-restate)

### P1 · 두 번째 모델을 쓰는 이유를 실측하기

검사 추천은 이미 인간 라벨과 첫 모델·보조 모델의 선택을 비교한다. 여기에 두 가지 자료를 더할 가치가 있다.

1. **검사 추천의 누락**은 일부 작업을 무작위로 골라 같은 코드·환경에서 등록된 전체 검사 묶음과 대조한다. 추천 밖에서만 발견된 반복 가능한 실패, 원래 기준 브랜치에서도 실패하는 검사, 간헐적 실패를 구별한다. 모든 검사가 통과한 작업에서 “생략해도 안전하다”는 학습 라벨을 만들지 않는다. 측정용 전체 실행은 비용 한도를 두고 격리한다. [추천 평가 코드](../agent_workflow/recommendation_records.py) · [Meta 사례](https://engineering.fb.com/2018/11/21/developer-tools/predictive-test-selection/)
2. **최종 코드 리뷰의 품질**은 알려진 결함이 있는 변경과 올바른 변경에서 검출률·잘못된 차단·검토 시간을 비교한다. 현재 리뷰 입력에 구현자 보고가 들어간다. 같은 후보를 새 세션에서 각각 검토하되 한 쪽에는 1차 판단 뒤에 구현 보고를 보여 주면, 보고서가 리뷰를 돕는지 선입견을 만드는지 비교할 수 있다. 이 실험은 이미 요구되는 독립 리뷰를 모두 수행하는 조건에서 진행한다. [리뷰 입력 생성](../agent_workflow/runner.py) · [CR-Bench-v2](https://arxiv.org/abs/2611.02566)

**결정 기준**은 추가로 잡은 실제 회귀 수, 추가 차단 오류 수, 추가 검토 분·모델 호출 수다. 모델·프로필·변경 유형별 관측 수를 함께 적는다. 실제로 누락할 수 있었던 실패가 거의 관찰되지 않는 표본에서는 자동 라우팅 변경을 결정하기 어렵다.

### P1 · 재개 화면과 모델 인계에 같은 근거를 주기

다음 세션에 우선 보여 줄 것은 원래 목표, 남은 조건, 마지막으로 유효한 근거, 다음 행동, 그 행동을 바꿀 수 있는 미확인 사항이다. 각 항목에서 원문으로 이동하도록 한다. 예컨대 “구현 응답이 끊겼다. 변경은 남아 있다. 현재 지문의 검사 결과가 없다. 등록 검사를 먼저 실행한다”면 지난 대화를 읽지 않고 재개할 수 있다.

기존 `pickup`을 기준선으로 잡고, 구조화된 짧은 인계를 더한 버전과 비교한다. 동일한 중단 지점의 독립 복사본을 준비하고 모드를 교차 배정한다. **첫 올바른 행동까지 걸린 시간**, 잘못 고른 작업, 재설명 횟수, 오래된 근거 사용, 인계 작성 시간을 기록한다. 인계가 짧아졌어도 운영 제약을 놓치거나 첫 행동을 틀리면 실패다. 사람용 화면은 ‘다음에 결정할 일’에서 관련 실행 구간으로 연결한다. [기존 측정 항목](../agent_workflow/resume_metrics.py) · [기존 인계](../agent_workflow/session_notes.py) · [StateHarness](https://arxiv.org/abs/2610.17616)

### P2 · 두 번째 프로젝트에서 목표 모드 일반화하기

현재 목표 모드는 `AGENTS.md`, `REFACTORING_SUPREME_DIRECTIVE.md`, `agent-context/session-handoff.md`, 거래 관련 금지 범위, 선택적 종목·마일스톤에 결합돼 있다. 재사용할 부분은 조건별 상태, 대기 입력, 반복 중단, 누적 예산, 검사·독립 리뷰, 완료 판정이다. 첫 후보는 자기 저장소의 **재개 시 오래된 근거를 표시하는 작은 변경**이다. 기존 개발 프로필은 handoff·release·dashboard 검사 묶음을 이미 제공한다. 파일 범위와 리뷰어를 명시한 목표용 프로필로 좁혀 쓸 수 있다. [Katakuri 계약](../agent_workflow/katakuri_goal.py) · [개발 프로필](../profiles/agent-workflow-development.json)

두 번째 프로젝트용 프로필에 목표 지침, 읽을 참조, 수정 허용 범위, 검증할 조건, 검토자, 외부 입력 종류를 선언하고 실행 시 버전을 고정한다. Git 작업공간과 SQLite 원장을 재사용한다. 기존 Katakuri 작업 ID로 상태 조회·재개·종료가 되고, 종목·마일스톤·로컬 개발 제한도 보존되는지를 회귀 조건으로 둔다. 새 프로젝트가 가짜 Katakuri 문서를 만들지 않고 작업 1건을 끝내면 일반화의 첫 근거가 된다. 세 번째 프로젝트나 두 번째 실행 호스트의 구체적 요구가 생길 때 플러그인·분산 큐의 범위를 정한다.

## 5. 첫 6주의 실행안과 채택 기준

기간은 한 팀이 순차 개발한다고 가정한 계획 단위다. 실제 소요 시간과 실행 비용은 첫 주의 사례 구성으로 추정한다.

| 기간 | 하나의 검증 가능한 산출물 | 다음 투자 판단 |
|---|---|---|
| 1주 | 4개 fixture, 독립 채점기, 현재 커밋 결과표. 기존 45개 테스트를 별도 기준으로 사용 | 잘못된 결과와 정상 구현을 구별할 수 있는가? 평가 자체가 애매하면 먼저 고친다. |
| 2주 | 한 프로필에서 조건→검사 결과 연결, 기존 판정과의 불일치 목록 | 필수 증거 부재를 발견하고 정상 완료를 잘못 차단한 원인을 설명할 수 있는가? |
| 3주 | 중단 지점 네 곳을 재현하는 fixture와 재개 진단 | 중복된 외부 효과·현재성 없는 완료가 1건이라도 관찰되면 자동 재개 범위를 확대하기 전에 수정한다. |
| 4주 | 대표 작업에서 현행·후보 하네스를 대응 비교. 첫 행동·개입·비용과 최종 결과를 기록 | 품질이 유지되면서 사람 개입 또는 재작업이 줄어드는 업무 유형이 있는가? 해당 유형만 다음 단계로 보낸다. |
| 5~6주 | 자기 저장소 한 프로필에서 목표 작업 1건. 여력이 있으면 검사 추천 표본 대조나 짧은 인계 중 비용이 큰 쪽 하나를 실험 | 두 번째 프로젝트 성공과 Katakuri 호환성이 확인되면 공통 목표 모드를 공개한다. 측정 개선이 없으면 기존 정책이 기준선이다. |

**실험 예산.** 실제 모델 비교의 제안 상한은 12개 사례 × 현행·후보 2개 × 독립 반복 3회 = 72회 **작업 시도**다. 한 시도 안에는 여러 모델 호출이 들어갈 수 있다. 먼저 개발용 4개를 한 번씩 대응 실행해 비용을 추정한다. 모델 버전·도구 버전·시작 커밋·환경·예산을 기록하고, 동일 모델 쌍과 서로 다른 새 worktree를 사용한다. 실행 순서를 교차하거나 무작위화하고, 채점자는 어느 방법의 출력인지 모르게 한다. 여러 변경을 동시에 켜지 않아야 개선 이유를 찾을 수 있다. 12개 사례 단위 결과와 불확실성을 함께 보고하고 같은 사례의 세 번을 독립 과제 세 개로 세지 않는다. [비용·보류 표본의 근거](https://arxiv.org/abs/2407.01502) · [반복 신뢰도](https://arxiv.org/abs/2406.12045)

| 보고할 지표 | 계산과 해석 |
|---|---|
| 잘못된 완료 | 독립 채점에서 실패했는데 완료 처리한 건수 / 완료 처리한 채점 가능 건수. 분모 0이면 미정. 관측 0건은 파일럿 통과 기준이며 모집단의 오류율 0을 뜻하지 않는다. |
| 누락된 정상 완료·올바른 대기 | 독립 채점상 완료 가능한데 차단한 건수와 실제 외부 자료 때문에 올바르게 기다린 건수를 각각 표시한다. 무조건 차단하는 정책이 유리해지는 것을 방지한다. |
| 반복 신뢰도 | 같은 조건에서 세 번 모두 기대 결과에 도달한 사례 수 / 세 번을 모두 계획한 사례 수. 결과를 얻지 못한 시도와 원인을 함께 표시한다. 완료가 정답인 과제와 대기가 정답인 과제는 나누어 보고한다. |
| 검증된 완료 1건당 비용 | 실패·재시도 포함 전체 모델 비용 / 독립 채점 통과 완료 건수. 별도로 사람의 작업 준비·개입·사후 검토 분을 같은 분모로 집계한다. 모델 비용 미보고분은 건수와 알려진 소계로 표시한다. |
| 재개 품질 | 첫 올바른 행동까지의 중앙값과 범위, 잘못 고른 작업·재설명·중복 외부 효과의 건수. 사람이 직접 한 일, 부모 에이전트 복구, 무인 재시도는 구분한다. |
| 지속 품질 | 후속 변경에서 깨진 기존 조건 수, 병합 후 재작업·되돌림. 관찰한 기간과 추적 가능한 작업 수를 명시한다. 로컬 완료와 병합·배포의 분모가 다르다. |

**투자 순서를 바꿀 근거.** 실측에서 대부분의 시간을 첫 프로젝트 연결에 쓴다면 이미 설계된 사용자 파일럿과 연결 개선을 앞당긴다. 실패가 대부분 외부 서비스 상태 불명에서 온다면 복구를 먼저 한다. 평가 데이터에서 어려운 일이 독립 읽기 작업으로 분해되고 통합 비용도 작다면 병렬 worker 실험을 시작한다. 여러 팀이 이미 쓰는 관측 백엔드로 내보내야 한다면 기존 실행 구간을 OpenTelemetry의 agent/workflow 구간에 매핑한다. 어느 경우에도 관측 이벤트 하나가 제품 조건 충족을 대신하지 않는다.
