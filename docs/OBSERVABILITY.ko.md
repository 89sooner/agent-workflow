# v0.4.0 에이전트 관제실 사용 안내

관제실은 agent-workflow가 실제로 호출한 구현 담당, 검사 실행기, 독립 리뷰, 통합·배포의 작업과 인계를 보여준다. 역할별 픽셀 작업실, 실행 그래프, 시간순 이벤트, 선택한 단계의 결과와 로그가 같은 기록을 사용한다.

Python 3.11 이상과 Git을 사용하는 기존 실행 환경을 유지한다. 대시보드 실행에 새 Python 패키지, Node 서버, 외부 관측 서비스 또는 CDN은 필요하지 않다. 화면 설계의 조사 근거는 [제품·연구 비교](OBSERVABILITY_RESEARCH.ko.md), 프로젝트 설정과 기본 자동화는 [v0.3 안내](AUTOMATION_V0.3.ko.md)를 참고한다.

## 1. 실행하고 작업을 선택하기

기존 설치에서 전경으로 대시보드와 큐 worker를 실행한다.

```bash
agent-workflow serve --port 8765
```

브라우저에서 `http://127.0.0.1:8765`를 연다. 왼쪽 목록에서 작업을 선택하면 해당 작업의 관제실이 표시된다. 별도 터미널에서 `run`, `check`, `release`를 실행한 경우에도 같은 상태 저장 경로를 사용하면 새 기록이 보인다.

백그라운드 실행은 다음과 같다.

```bash
agent-workflow daemon start --port 8765
agent-workflow daemon status
agent-workflow queue WP-074
agent-workflow jobs
```

상태 저장 경로를 분리해서 사용한다면 모든 명령에 같은 `--home`을 지정한다.

```bash
agent-workflow --home /path/to/workflow-state daemon start --port 8765
agent-workflow --home /path/to/workflow-state queue WP-074
```

기본 상태 경로는 `~/.local/state/agent-workflow`다. `serve`와 `daemon start`는 큐 worker도 시작하므로 기존 대기 작업이 있으면 실행 조건을 만족하는 작업부터 처리할 수 있다. 브라우저에서 기록만 열거나 재생하는 행동은 작업을 새로 실행하지 않는다.

같은 상태 경로의 기본 worker는 작업을 순서대로 처리한다. 화면에 여러 역할이 있다고 해서 여러 모델이 동시에 실행되는 것은 아니다. 별도 worktree나 별도 상태 경로에서 실행하는 경우의 잠금·예약 규칙도 그대로 유지된다.

## 2. 화면에서 확인할 수 있는 것

### 역할별 작업실

| 역할 | 화면이 나타내는 주체 | 확인할 정보 |
|---|---|---|
| 컨트롤러 | 작업 순서와 증거를 관리하는 agent-workflow | 환경 준비와 실행 지시·결과 수신 |
| 구현 | 작업에 지정된 `claude` 또는 `codex` | 현재·최근 구현 호출과 결과 |
| 독립 리뷰 | `claude`, `codex`, `codex-session` 중 지정된 검토 역할 | 리뷰 호출, 통과·수정 요청·중단 |
| 검사 실행기 | 등록된 실제 검사 명령 | 실행 시간, 종료 코드, timeout, 검사 결과 |
| 통합·배포 | 병합 결과 검사, 배포 명령, health 명령 | 어떤 revision을 검사·배포했는지와 결과 |

`codex-session`은 독립 검토 세션이라는 역할 계약을 그대로 표시한다. 같은 Codex라는 이유로 구현 역할과 하나의 호출로 합치지 않는다. `reviewer=none`인 작업에서는 독립 리뷰를 수행한 것처럼 표시하지 않는다.

활동 표시는 기록된 실행 단계에 근거한다. 연결이 끊기면 마지막 기록을 유지하고 활동 표시를 멈춘다. 종료 기록 없이 관측 소유 프로세스가 사라진 단계는 `unknown`으로 표시한다. 다른 프로세스가 같은 PID를 재사용해도 이전 실행의 생존 근거로 삼지 않는다. 모델 제공자의 서버에서 처리가 계속되는지까지 확인하는 기능은 아니다.

### 실행 순서와 역할 개요

기본 “실행 순서” 보기는 실제 명령 호출을 각각의 단계로 표시한다. 검사 실패 뒤 구현을 다시 호출하고 재검사했다면 각각 다른 단계로 남는다. 예정된 검증이나 수행하지 않은 리뷰를 완료된 node로 추가하지 않는다.

“역할 개요”는 같은 역할의 호출을 합쳐서 보여준다. 어떤 역할이 반복되었고 주의할 결과가 있는지 빠르게 살펴볼 수 있다. 정확한 실행 순서와 개별 실패를 확인할 때는 “실행 순서”로 돌아간다.

그래프의 실선은 컨트롤러가 다른 역할로 결과를 넘긴 순서, 점선은 같은 역할의 다음 실행을 뜻한다. 에이전트끼리 직접 대화했다는 표시가 아니다. 실제 구현은 컨트롤러가 각 CLI를 호출하고 구조화된 결과·검사 결과·리뷰 피드백으로 다음 단계를 결정한다.

한 작업 안의 실행 흐름을 표시하는 기능이며, 모든 프로젝트와 task 의존성을 한 화면에 연결하는 전역 DAG 편집기는 아니다. 기존 dependency 기능은 실행 조건으로 유지되지만 전체 의존성 그래프를 새로 편집하는 기능은 포함하지 않는다.

### 시간순 이벤트와 선택 상세

작업실의 역할, 그래프 node 또는 이벤트를 선택하면 상세가 연결된다. 입력 목표와 완료 조건, 구조화된 반환 결과, 리뷰 findings, 명령의 종료 코드·timeout·소요 시간, 공급자가 보고한 사용량 등을 가능한 범위에서 확인할 수 있다.

이벤트는 단조 증가 순번을 기준으로 정렬한다. 같은 초에 여러 사건이 발생해도 순번으로 구분한다. 검색은 현재 불러온 이벤트의 역할·내용·순번을 대상으로 한다. 더 이전 기록은 “이전 기록 불러오기”로 조회한다.

사용량이나 비용이 제공되지 않으면 알 수 없음으로 남는다. CLI가 보고한 token·금액과 측정한 실행 시간을 사용하며, 모델 가격표로 추정한 비용을 실제 청구액처럼 표시하지 않는다.

### 실행 선택과 JSON 내보내기

같은 task를 재개하면 새로운 실행 기록이 생길 수 있다. “현재 실행 따라가기”는 살아 있는 실행을 우선하고, 없으면 최신 실행을 선택한다. 실행 목록에서 과거 실행을 고르면 해당 기록을 확인한다. CLI의 `run`/`pipeline`은 구현·검사·리뷰·자동 릴리스·마감을 하나의 run으로 묶는다. 별도로 `release`를 호출하면 그 호출과 마감이 하나의 새 run이 된다. 중첩된 내부 호출 때문에 같은 실행을 여러 run으로 나누지 않는다.

라이브러리 함수 `execute()`나 `release_task()`를 독립적으로 호출하면 각각 관측 문맥을 시작한다. 큐 worker가 실행한 경우에는 같은 task의 실제 `running` job을 확인한 뒤 `job_id`를 연결한다. 환경변수의 임의 ID만으로 다른 job과 연결하지 않는다.

“JSON 내보내기”는 선택한 실행의 구조화된 기록을 내려받는다. raw prompt나 전체 로그 파일을 묶은 백업은 아니다. 아래의 응답 크기 제한을 적용하므로 전체 DB를 무제한으로 내보내는 기능으로 해석하지 않는다.

## 3. 기록 재생과 실제 재실행은 다르다

“기록 재생”, 이전·다음 버튼, 시간 슬라이더는 관측 커서만 움직인다. 모델 호출, 파일 수정, 큐 등록, 배포 또는 재시도를 일으키지 않는다. 해당 시점까지 관측한 단계와 이벤트를 보여주며 “실시간으로”를 누르면 최신 기록으로 돌아간다.

이미 완료된 span도 과거 시작 시점에서는 “당시 실행 중”으로 보일 수 있다. 정확한 시작·종료 이벤트가 이전 페이지에 있어서 같은 초의 경계를 확정할 수 없다면 불확실성을 표시한다. 이 기능은 전체 운영 상태나 Git 작업 폴더를 과거 상태로 복원하는 것이 아니다.

로그 열기는 별도 동작이다. 재생 중 열어도 현재 저장된 로그 파일을 읽으므로 선택한 과거 시점 이후의 내용이 포함될 수 있다. 화면에 이 차이를 표시한다.

실제로 다시 실행하려면 작업·실행의 현재 상태를 확인하고 기존 `run`, `resume`, `queue`, `release` 명령이나 해당 제어를 사용한다. 완료한 task의 새 작업 범위는 새 task로 등록한다.

## 4. 과거 성공과 현재 증거를 구분하기

| 정보 | 의미 | 의미하지 않는 것 |
|---|---|---|
| Run/span의 성공 | 기록된 호출이 해당 결과로 종료됨 | 현재 파일이 그대로라는 보장 |
| Task의 `completed` | 당시 등록 검사·지정 리뷰가 통과함 | PR 병합이나 배포 완료 |
| 현재 증거 유효성 | 현재 코드·참조 입력·금지 경로와 기록된 증거의 일치 여부 | 모든 외부 환경·데이터의 동일성 |
| `release.merge_commit` | 기록된 병합 effect와 SHA | 병합 결과의 통합 검사 통과 |
| `integration_verification.passed` | 지정한 병합 SHA·검사 계약에 연결된 통합 검사 결과 | 운영 서비스가 계속 정상이라는 보장 |
| `deployed_revision`과 health 결과 | 해당 배포 및 상태 확인에서 기록한 revision·결과 | 지속적인 외부 운영 모니터링 |

작업 폴더가 없어졌거나 Git 상태 조회가 실패하면 “현재 상태 관찰 불가”와 이유를 표시한다. 과거 `completed` 기록은 보존하지만 무기한 로딩이나 현재 통과로 표시하지 않는다. 작업 폴더를 복구한 뒤 다시 조회하면 현재 유효성을 재평가한다.

## 5. 수동 보류, 실행 중단, 오류 상태

| 행동·상태 | 대상 | 동작 |
|---|---|---|
| `hold TASK_ID --reason ...` | Task | 기존 대기 작업의 claim과 다음 실행 단계 시작을 막는다. 사유를 저장한다. |
| `unhold TASK_ID` | Task | 보류를 해제한다. 기존 queued 작업은 다시 실행될 수 있다. |
| `stop JOB_ID` | 특정 큐 실행 | 해당 실행의 관리 프로세스에 중단을 요청한다. |
| `cancel JOB_ID` | Queued 실행 | 아직 시작하지 않은 실행을 취소한다. |
| `resume JOB_ID` | 실패·중단·취소된 실행 | 기존 옵션과 기한을 확인하여 새 실행을 등록한다. task hold는 별도로 해제해야 한다. |
| `blocked` | Task 결과 | 실패나 입력 필요의 기록이다. 수동 보류 자체를 뜻하지 않는다. |
| `batch pause NAME` | Batch | 다음 작업 예약을 멈춘다. 이미 queued/running인 실행의 개별 중단과 다르다. |

```bash
agent-workflow hold WP-074 --reason '다음 단계 전에 변경 범위를 확인한다'
agent-workflow show WP-074
agent-workflow unhold WP-074
```

보류는 이미 실행 중인 모델·검사 명령을 강제로 종료하는 명령이 아니다. 현재 실행의 결과를 기록한 뒤 다음 경계에서 멈춘다. 해당 프로세스도 중단해야 한다면 `jobs`에서 실행 ID를 확인하고 `stop JOB_ID`를 사용한다. 어느 동작도 이미 발생한 파일 변경·push·merge·배포를 자동으로 되돌리지 않는다.

`checkpoint --blocked`는 차단 상황을 기록하는 기능이다. 작업을 지속적으로 멈춰 두려면 `hold`를 사용한다. 보류는 별도 DB 제어 행에 저장되므로 오래된 task snapshot을 저장해도 보류가 사라지지 않는다.

## 6. 관측 데이터와 API 계약

구현 근거: [observability.py](../agent_workflow/observability.py), [core.py](../agent_workflow/core.py), [usage.py](../agent_workflow/usage.py), [server.py](../agent_workflow/server.py).

| 기록 | 목적 |
|---|---|
| `tasks`와 기존 `events` | 작업 계약·검사·리뷰·완료·릴리스의 원장과 변경 이력 |
| `observation_runs` | 관측한 controller 호출의 시작·종료·결과 및 task 연결 |
| `observation_spans` | 실제 관리 명령의 역할, 이전 단계, 시작·종료·시간·결과 |
| `observation_events` | 실행 지시, 결과 반환, 체크포인트, 복구·보류 등 시간순 활동 |
| `task_controls` | 실행 중에도 유지되는 수동 보류 제어 |

관측 기록은 원장의 완료 조건을 대신하지 않는다. 검사·독립 리뷰·fingerprint 검증은 기존 core/runner가 판단한다. 관측 조회만으로 task를 완료하거나 release를 진행하지 않는다.

관측 응답의 `schema_version`은 `1`이다. 주요 필드는 `task`, `runs`, `selected_run_id`, `spans`, `events`, `edges`, `actors`, `coverage`, `warnings`, `pagination`이다.

| 읽기 API | 용도 |
|---|---|
| `GET /api/observability?task_id=WP-074` | 살아 있는 실행을 우선하고, 없으면 최신 실행의 관측 기록 |
| `GET /api/observability?task_id=WP-074&run_id=RUN_ID` | 지정 실행 조회 |
| `GET /api/observability?task_id=WP-074&run_id=RUN_ID&before=SEQ&limit=200` | 더 이전 이벤트 조회 |
| `GET /api/observability/export?task_id=WP-074&run_id=RUN_ID` | 선택 실행의 제한된 JSON export |
| `GET /api/observability/artifacts/SPAN_ID/stdout` | 선택 단계의 표준 출력 끝부분 |
| `GET /api/observability/artifacts/SPAN_ID/stderr` | 선택 단계의 표준 오류 끝부분 |
| `GET /api/tasks/WP-074` | 현재 task, Git 관측 결과, 증거 유효성 |

`before`는 양의 이벤트 순번이며 그보다 작은 이벤트를 반환한다. `pagination.next_before`와 `has_more`를 사용한다. 지정 run은 해당 task에 속해야 한다. 명령·임의 경로를 받는 범용 파일 읽기 API는 아니다.

| 범위 | 제한 |
|---|---:|
| 실행 선택 목록 | 최근 30개 run 및 목록 밖의 현재 실행·명시한 실행 |
| 기본 이벤트 응답 | 최근 200개 |
| `limit` 허용 범위 | 1~500 |
| 일반 응답 span | 최근 250개 |
| 브라우저가 보관하는 이벤트 | 최대 5,000개 |
| JSON export span | 최대 5,000개 |
| JSON export 이벤트 | 최대 10,000개 |
| 개별 stdout/stderr 응답 | 마지막 65,536 bytes, 즉 64 KiB |

잘린 범위는 경고와 truncation/pagination 정보로 표시한다. `run_id`를 알고 있으면 목록보다 오래된 해당 실행도 직접 조회할 수 있지만, 실행 목록 전체를 페이지로 탐색하는 기능은 없다. 오래된 이벤트를 추가로 불러와도 일반 그래프의 span 상한은 별도로 유지된다.

관제실은 보이는 탭에서 정상 연결 시 약 2초마다 갱신한다. 오류 시 재시도 간격을 늘려 최대 30초로 제한하고, 숨겨진 탭에서는 관제실 polling과 재생을 멈춘다. 이는 WebSocket/SSE 스트리밍이나 프레임 단위 실시간 보장이 아니다.

## 7. 관측 범위와 원문 취급

기본 관측 범위는 `coverage.source="controller"`다.

| 포함 | 포함하지 않음 |
|---|---|
| 컨트롤러가 호출한 구현·독립 리뷰·검사·setup·통합 검사·배포·health | Claude/Codex CLI 내부의 모든 tool call |
| 호출 순서, 구조화된 결과, 실제 명령 결과 | CLI 내부 subagent의 전체 계층과 통신 |
| 컨트롤러를 통한 작업 지시와 결과 인계 | 기록되지 않은 에이전트 간 직접 대화 |
| 측정한 소요 시간, 공급자가 보고한 token·비용 | 모델 내부 생각, 추정 청구액을 확정 금액으로 표시하는 기능 |
| 선택한 단계의 stdout/stderr 열람 | raw prompt·전체 transcript를 기본 응답에 복제하는 기능 |

로그는 사용자가 “출력 로그 열기” 또는 “오류 로그 열기”를 눌렀을 때 읽는다. 등록된 span의 작업 디렉터리와 로그 종류를 확인하고 작업 밖의 경로·symlink 우회는 거부한다. 로그 원문에는 실행 프로그램이 출력한 민감한 내용이 포함될 수 있으므로 기본 관측 metadata와 같은 공개용 요약으로 취급하지 않는다. 원문 전체를 자동으로 비식별화한다는 보장은 없다.

대시보드는 loopback, Host/Origin 검사, 변경 요청 토큰, 동일 출처 정적 자산을 사용한다. 다중 사용자 인증·권한 분리 서비스는 아니며 같은 OS 계정에서 실행되는 프로그램들을 격리하지 않는다.

## 8. 기존 평가에서 보완한 실행 계약

| 이전에 확인한 문제 | 반영한 동작 |
|---|---|
| Git ignore된 `.env` 등 forbidden 경로 변경을 놓침 | 명시한 금지 경로의 존재·내용·mode·symlink를 별도 hash로 비교. 원문은 원장에 복사하지 않음 |
| 기존 queued 작업을 `blocked` 기록만으로 보류할 수 없음 | `hold`/`unhold`와 별도 durable control 도입. claim 및 단계 경계에서 확인 |
| 자동 finalize가 오래된 task로 새 release 설정을 덮을 수 있음 | Task revision 비교 저장과 잠금 안의 재조회로 오래된 저장 거부 |
| 병합 검사에서 HEAD를 바꿔도 clean이면 배포 가능 | 병합 SHA·index·실제 내용과 보호 경로를 검사·배포 경계에서 확인 |
| 배포 없는 merge가 검사 없이 후속 성공으로 인정됨 | Local은 기준 브랜치 push 전 검사. GitHub는 실제 병합 SHA 검사. 배치·merged 의존성은 통합 receipt 요구 |
| 릴리스 시작 때만 실행 시간대를 확인함 | 하나의 릴리스 deadline과 단계별 window/hold/누적 시간 확인 |
| Local merge 후 receipt 저장 전 중단하면 재개 불가 | 병합 전 intent를 저장하고 소유 작업 폴더·부모·후보를 검증해 재개. 수동 변경은 보존 |
| 선택적 알림 준비 실패가 큐 worker까지 종료시킴 | 알림 준비·전달 오류를 실패 기록으로 분리. 핵심 DB 저장 오류를 무조건 삼키지는 않음 |
| 작업 폴더 조회 실패가 계속 확인 중으로 표시됨 | 현재 관찰 불가와 구체적인 이유 표시, 과거 완료 이력 보존 |
| 잘못된 profile 타입에서 Python traceback이 노출됨 | 필드별 타입 검증과 사용자가 이해할 수 있는 입력 오류 |
| 외부 참조 문서 내용이 바뀌어도 증거가 유지됨 | 참조 파일 내용·존재·링크 지문을 검사·리뷰·완료·릴리스 증거와 연결 |

릴리스 명령의 검사·배포·health는 managed usage에 포함된다. `release --timeout`은 한 릴리스 호출의 전체 기한이며 각 단계에서 새로 시작하지 않는다. Git/API와 서비스 준비도 이 기한을 적용한다. 관리 명령의 누적 시간과 전체 호출의 벽시계 시간은 서로 다른 수치다.

명시한 금지 경로가 프로젝트 내부의 심볼릭 링크라면 링크 정체성과 대상 내용·권한을 함께 확인한다. 내부의 깨진 링크는 대상이 없는 상태를 기준으로 기록한다. 금지 경로 자체나 부모 링크가 프로젝트 밖을 가리키면 외부 파일을 읽지 않고 등록·실행을 거부한다. 순환 링크와 내용을 검증할 수 없는 특수 파일도 거부한다.

GitHub 병합 뒤 통합 검사에서 실패하면 이미 일어난 `merged` 사실은 보존하고 배포·후속 성공 판정을 막는다. 원격 기준 브랜치에 들어가기 전의 강한 통합 보장은 GitHub branch protection·merge queue 등 저장소 운영 설정과 별도로 연계해야 한다. 배포 결과가 불명확할 때 자동 재실행하지 않는 기존 계약도 유지한다.

## 9. 업그레이드와 이전 작업

새 버전을 같은 상태 디렉터리에서 열면 기존 SQLite에 필요한 필드를 추가한다. `tasks.revision`과 제어·관측 테이블을 생성하며 기존 task·event·job 및 증거 파일을 지우지 않는다. 오래된 기록에서 존재하지 않았던 실행 시간이나 대화를 추정해 채우지는 않는다.

업그레이드 전에는 같은 상태 경로를 쓰는 이전 데몬·전경 실행을 종료하고 상태 디렉터리를 백업한다. 실행 중이던 작업은 실제 변경과 외부 effect를 확인한 후 명시적으로 재개한다. 서로 다른 버전의 writer를 같은 DB에 동시에 연결하지 않는다.

```bash
agent-workflow daemon stop
# 상태 디렉터리와 작업 폴더를 확인·백업한 뒤 새 소스로 갱신한다.
agent-workflow doctor
agent-workflow daemon start --port 8765
```

별도 `--home`을 사용했다면 중지·시작에도 같은 경로를 지정한다. WSL·Windows 자체 부팅과 로그인 예약을 설정하는 변경은 포함하지 않는다.

| 기존 task 상태 | 처리 |
|---|---|
| 단계별 run/span이 없는 이전 작업 | Legacy 이벤트를 표시. 없는 graph·소요 시간·대화는 만들지 않음 |
| 참조 문서가 없는 이전 작업 | 새 참조 지문을 만들기 위한 별도 절차가 필요하지 않음 |
| 참조 문서가 있고 아직 진행 중이나 옛 검사·리뷰에 참조 지문이 없음 | 현재 참조를 읽고 `check`와 독립 리뷰를 갱신 |
| 완료한 이전 작업의 참조 증거가 새 계약과 맞지 않음 | 과거 완료를 보존하고 새 task로 검증 |
| `forbidden_paths`가 있으나 등록 당시 보호 경로 기준 hash가 없음 | 과거 기준을 복원할 수 없으므로 새 task로 등록 |
| 이전 local merge candidate receipt만 있고 intent가 없음 | 저장된 후보·부모·소유 작업 폴더를 검증하고 통합 검사를 수행하여 재개 |

외부 참조가 있는 수동 리뷰를 가져올 때는 검토 시작 시점의 코드와 참조 지문을 모두 전달한다.

```bash
agent-workflow show WP-074
agent-workflow review-import WP-074 --file /path/to/review.json \
  --reviewer codex --fingerprint CODE_FINGERPRINT \
  --refs-fingerprint REFERENCE_FINGERPRINT
```

실제 검토한 입력에 대한 지문을 사용한다. 새 지문만 기존 리뷰에 붙여서 통과시키는 절차가 아니다. `codex-session`은 기존 독립 실행 receipt 요구도 그대로 유지된다.

## 10. 개발 검증과 적용 한계

표준 라이브러리 테스트와 관제실 통합 시나리오는 다음 명령으로 실행한다.

```bash
python3 -m unittest discover -s tests -v
python3 tests/observability_integration.py
```

관제실 통합 테스트는 임시 작업과 로컬 서버에서 기록·API·브라우저의 연결을 검사한다. 모델 과금이나 운영 배포를 호출하는 live 검증과 구분한다. 브라우저 검증에는 선택적 개발 의존성인 Playwright가 필요하며 CI의 고정 검증 버전은 `1.51.1`이다. 사용자용 CLI와 대시보드의 runtime 의존성에는 추가되지 않는다. 로컬 실행 결과와 검증 범위는 [v0.4 검증 기록](verification-v0.4.json), 해당 commit의 CI 결과는 GitHub Actions에서 확인한다.

실제 CLI 계정·모델 연결은 기존 `tests/live_smoke.py`, 외부 운영 릴리스는 사용자가 지정한 대상과 권한에서 별도로 검증한다. 이 문서는 실제 사용자 환경의 WSL 재부팅, 장기간 상주 운용, 운영 GitHub merge·배포가 검증되었다고 주장하지 않는다.

현재 화면은 한 작업과 선택한 실행을 자세히 보는 데 맞춰져 있다. CLI 내부 subagent 관측, 전역 task DAG 편집, OTLP export, 다중 사용자 접근 제어, 무제한 로그·trace 저장 관리, 사용자 생산성 개선의 정량 평가가 필요하면 각각의 별도 계약과 검증을 추가해야 한다.
