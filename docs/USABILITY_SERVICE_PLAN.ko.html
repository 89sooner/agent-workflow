01 · 사용성 개선은 일부 이루어졌지만, 서비스 수준의 시작 경험은 부족하다

확인한 개선

  • 실행 그래프와 3D 선택, 담당자 상세가 연결된다.
  • 과거 실행·로그·이벤트 재생을 한 화면에서 탐색한다.
  • 접속 오류·숨긴 탭·움직임 줄이기를 처리한다.
  • 관측 화면은 GET만 사용하며 실제 기록과 추정을 구분한다.

남아 있는 핵심 부담

  • 사용자가 state home과 watch/serve 차이를 알아야 한다.
  • 작업을 원장에 남기는 책임이 사용자 또는 에이전트 프롬프트에 있다.
  • 다른 원장에 기록하면 같은 프로젝트여도 다른 화면 범위에 머문다.
  • “왜 안 보이는가”를 UI 대신 문서와 CLI로 진단한다.

판단 근거: 소스와 실제 8777 화면의 동선 점검이다. 실제 신규 사용자 인터뷰나 사용성 실험 결과는 아니다. “사용자가 모두 실패한다”거나 전환율이 나쁘다는 수치는 아직 없다.

문제실제 관찰사용자에게 생기는 비용
첫 연결이 기술 설정원장 경로, 서버 모드, 포트를 문서에서 선택일을 시작하기 전에 도구 운영을 배워야 함
관측과 실행의 동선 단절/mission → “작업 등록·실행 관리” → 8777 /에서 새 작업 버튼 비활성연결은 됐는데 다음 행동을 할 수 없는 이유를 찾아야 함
프로젝트 식별이 어려움프로젝트 선택기에 경로 말단 이름 26개; 오래된 worktree도 포함실제 제품 이름과 현재 작업을 매번 대응시켜야 함
긴 ID·목표가 정보 위계를 차지작업 목록에서 긴 영어 목표와 ID가 줄바꿈됨누가 막혔는지, 지금 내가 할 일은 무엇인지 늦게 파악
3D 정보 가독성1280×800 화면에서 넓은 3D 영역 대비 작은 이름표; 그래프·이력은 아래쪽보기 좋은 공간과 빠른 판단 사이의 균형 부족
미발견과 빈 상태 혼동소스에 “원장을 찾는 중”, “표시할 작업이 없습니다” 중심 안내원장 없음·필터 결과 없음·연결 실패를 구별하기 어려움

대안 가설 검토: HTTP 자산 제공 실패가 주원인은 아니다(실제 200, 정상 렌더링, 실패 요청 0). 기능 자체가 없는 것도 아니다(그래프·선택·이력은 존재). 남은 주요 가설은 연결·정보 구조의 인지 부담이다. 신규 사용자 실험에서 대부분 안내 없이 빠르게 연결·진단한다면 이 우선순위를 낮춘다.

02 · 목표 사용자 경험

개인 개발자

한 프로젝트에서 Codex·Claude·OpenCode를 쓰며, 수동 작업 등록 없이 진행·중단 이유를 확인하고 싶다.

여러 작업을 맡긴 관리자

서로 다른 worktree·도구에서 진행 중인 일과 확인 요청을 한 곳에서 보고, 증거를 확인한 뒤 다음 행동을 정한다.

  1. 첫 실행: 프로젝트 폴더를 선택하면 알려진 연결 후보를 제시한다. 서버가 로컬 브라우저의 임의 파일 경로를 읽을 수 있다고 가정하지 않는다. 로컬 helper/명시적 폴더 경로 연결 중 지원 방식을 안내한다.
  2. 연결 확인: “OpenCode 연결됨 · 새 세션 자동 표시”, “Claude는 workflow 실행만 관측”처럼 도구별 능력을 보여 준다. 연결을 감지했다는 사실과 관측 동의를 분리한다.
  3. 작업 시작: 기존 도구를 그대로 사용하는 ‘관측’과 agent-workflow에 실행을 맡기는 ‘관리 작업’을 구분한다. 관측 세션에 목표·검사 조건을 억지로 요구하지 않는다.
  4. 재방문: 최근 프로젝트·필터·선택을 복원하고, 종료된 세션은 접는다. 원장 경로는 연결 상세로 옮긴다.
  5. 문제 해결: 연결 끊김 / 미지원 도구 / 권한 필요 / 해당 프로젝트 아님 / 기록 없음 각각에 원인·마지막 성공 시각·다음 행동을 표시한다.

04 · OpenCode: 이번 구현과 다음 단계

구현된 관측 범위

  • 로컬 서버 URL + 프로젝트 디렉터리 한 번 연결.
  • 새 세션 자동 발견, 선택한 응답의 실제 agent·모델·도구 상태.
  • 네이티브 세션 ID와 응답별 이력, 부모 세션 관계.
  • 프로젝트 분리, 연결 해제, 인증 환경변수, 조회 실패 안내.
  • 기존 workflow DB에 task/job 생성 없이 GET으로 관측.

현재 한계와 다음 작업

  • UX-01~03 구현: 화면 연결·오류 진단·권한별 동선 안내. CLI도 유지한다. 운영 적용은 별도다.
  • polling snapshot이며 SSE 수집·영구 이력·재생은 아직 없다.
  • 상세 이름·도구는 세션을 선택한 뒤 조회한다.
  • OpenCode 1.3.17 실제 검증. 다른 1.x 버전은 응답 계약 확인 필요; 2.x 별도 어댑터 필요.
  • 프롬프트 발송·승인 응답·세션 중단 등 제어 기능은 포함하지 않는다.

공식 HTTP API의 /global/health, /session, /session/status, 세션 메시지 조회를 이용한다. SDK를 쓸 경우 기존 서버용 클라이언트와 새 서버를 만드는 생성자를 구분해야 한다. 플러그인과 SSE는 이벤트 수집 대안이지만 이번 구현은 연결된 서버를 조회한다. 서버 API · SDK · 플러그인

연동 대안장점비용 / 선택
HTTP snapshot기존 세션에 붙고, 원래 실행을 바꾸지 않음이번 선택. 짧은 중간 상태를 놓칠 수 있음을 표시
SSE + snapshot 복구활동·승인·도구 상태 변화와 더 빠른 갱신후속. 재연결·중복·과거 누락 처리 필요
OpenCode plugin도구별 lifecycle을 직접 수집할 여지설치·버전·훅 실패가 사용자 실행에 주는 영향 관리 필요
내부 DB/대화 파일 직접 파싱서버가 없어도 파일을 찾을 수 있음초기 지원에서 제외. 비공개 형식·잠금·개인정보·버전 호환 비용

busy → 실행 중, idle → 응답 대기, retry → 재시도 대기. HTTP 단절 → 연결 확인 필요. 응답 완료는 작업의 테스트 통과·리뷰 승인·배포 완료를 뜻하지 않는다. native agent 이름과 세션 제목, 공급자 모델 이름도 서로 다른 필드로 취급한다.

05 · 도구별 관측과 관리 작업을 분리한다

관측 영역

Source → Project → Native Session → Response / Tool. 명시적으로 연결한 출처에서 확인한 사실만 기록한다. 키는 source ID + native ID. 마지막 수집 시각·관측 가능 범위를 보존한다.

관리 영역

Task → Run → Check → Review → Release. 목표·완료 조건·검사·실행 권한이 필요한 관리 계약이다. 관측 세션을 관리 작업으로 전환하거나 연결하는 행동은 별도 명시적 동작으로 둔다.

초기 서비스 형태: 로컬 개인용 제품을 먼저 완성한다. Python·SQLite와 React·TypeScript·R3F는 유지한다. 현재 불편의 주요 원인은 언어가 아니라 연결·상태·정보 구조다. 프레임워크 교체를 먼저 하면 검증 범위만 커진다.

공유 서비스 단계: 사용자의 localhost를 클라우드 웹 서버가 직접 읽을 수 없다. 사용자 PC의 collector가 선택한 metadata만 인증된 외부 API로 보내도록 별도 경계를 만든다. 계정·프로젝트별 격리, 읽기/실행 권한, 보관 기간, 삭제·내보내기, 세션·도구 출력의 수집 범위를 제품 설정으로 제공한다. 기존 loopback 서버를 그대로 외부 공개하는 것은 이 계획의 배포 방식이 아니다.

관측 비용: 연결당 갱신 한도·backoff·보이는 탭 우선, 전체 이력은 pagination, 3D는 선택·실행 중 대상만 렌더링. 200개 세션 이상은 잘림을 명시하고 후속 cursor 조회를 제공한다. 무제한 디스크 검색이나 사용자가 모르는 서버 자동 실행은 도입하지 않는다.
